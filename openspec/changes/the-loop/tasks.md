Order follows design.md — Migration Plan, with one correction the plan implies:
the scenario runner is built in group 2, because every later group verifies
through it. Spec references are `<capability>` paths under `specs/`; scenario ids
are the model's `conformance/`; `contract/<name>` is a file of
`conformance/contract/`. Every verification is a `cargo test` name, a scenario id
or a command.

## 18. The member's client

A.40 (319-326) and 293a were ratified 2026-09-10. The page's bundle is
also a user-interface resource of the tool server, which a member's own
client renders inline; a tap inside a rendered view is a tool call
through that client, checked by the same rules as any other call.

Two things the review of this group established, which the tasks below
take as settled. First, 293 already says the tool server "is a remote
server of the model context protocol", and groups 7.1 and 7.8 built only
the in-process caller and an HTTP route, so the protocol shape itself is
unbuilt and 18.1 cannot stand on it; 18.0 builds it. Second, the served
page "runs no script at all" by the code's own gloss on 310, but 310 says
only that the page holds no client state a reload loses and that the
bundle carries no dependency fetched from anywhere else. Neither forbids
script. The bridge a rendered view needs is therefore admissible: it
holds no state a reload loses and fetches nothing external, and the gloss
in `page.rs` is what gives, not the requirement.
