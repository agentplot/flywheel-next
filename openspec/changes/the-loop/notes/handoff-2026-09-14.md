## What the operator can do today

Apply a scenario into a fresh instance, serve it, read a rail of real
decisions, answer them with one tap, watch the board move, open an
object in the dock, read a session's deliverable, and step a tour one
action at a time with the scenario's own copy on an overlay.

Measured on a real host: a click is about half a second, an idle page
load is 0.02 s, an idle instance writes no commits, and one "yes all"
over eight decisions cascades 125 commits of real work and settles.

## The lesson that cost the most, twice

**A test that passes is not evidence that the thing works.** Group 14
shipped a page reading "nothing" in every column with a green
`page_carries_the_mockups_regions`, because an element id can be present
on an empty region. Serve it and look at it.

The deeper form of the same thing: of the model's 200 atoms, 45 were
answered only by the scenario harness and by no real binding, so for
those the acceptance set could not fail — the double answered for the
code under test. Three defects came out of that gap in one day. The
parity gate now fails on any atom a machine guard names that no real
binding answers, with legitimate later-phase atoms carried in an explicit
deferred set. **Do not add to that deferred set casually.**

Two more defects were found only by running against a live host rather
than in process: a forwarded chat message started a reader session it did
not need, and a question decision's reply field was stripped to an
unreadable box. `scenarios/rail-mockup.yaml` has no question decision, so
nothing in the suite could see the second. Running it for real is not a
formality.

## Open, and what each is blocked on

- **Stages 4 and 5 of the storefront scenario** — construction and
  landing. Blocked on binding five `stage.*` / `item.*` reads that today
  only the scenario store answers. The decision to bind them was taken;
  the work was not started.
- **The tour's clock.** A stepped action is stamped at wall time, so an
  operator clicking through fifteen actions in three minutes sees a
  capture that should be days old read as three minutes old. `--through`
  back-dates correctly; stepping does not. The shape of the fix is a
  negative skew on `Host` starting at −(per_action × remaining) and
  closing to zero, so the clock only moves forward. Not built, on purpose
  — it changes `apply`'s start computation, which
  `an_apply_ends_at_the_present_and_ages_what_came_before` pins.
- **`offers::record`** makes a record for a finding only when an intent
  or a bolt is above the session, and its own doc says anything else
  should take another path, which is unimplemented. An offer nothing can
  record pins its session in `working` for ever, so a curation session
  offering a finding would deadlock.
- **Group 18**, the member's client, entirely.
- **Group 15**, the Discord wire, which needs Chuck's bot token.
- **Group 12**, the phase gate, which needs a week of his real use.

## Traps

`cargo test` may not rebuild after an edit — touch the file and re-run
before believing a result. An `eprintln!` inside an axum handler on a
spawned tokio thread does not reliably reach `cargo test` output; write
to a file. A 390px screenshot taken with Chrome's `--window-size` lays
out wider than it claims and crops, reporting overflow that does not
exist — drive a phone viewport through `Emulation.setDeviceMetricsOverride`
over CDP instead.

## How to run sessions on this

One session per worktree, never two in one checkout. Three sessions in
one tree cost sixteen conflict hunks in a day, and two of them fixed the
same three defects independently without knowing.

Give a session an objective and let it own it. A decomposed task list
reviewed task by task produced a page that passed every test and that
nobody could use.
