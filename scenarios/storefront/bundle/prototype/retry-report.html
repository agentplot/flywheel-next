Retry schedule: what a delayed retry would have recovered

Fourteen days of recorded checkout attempts, replayed against the processor's sandbox, which returns decline codes. Throwaway prototype for intent/storefront-declines.

What was run

41,900 recorded authorization attempts were replayed against the sandbox account, which answers with the same two-character decline codes production returns and which production discards. Each declined attempt was then re-offered on eight candidate schedules. The sandbox's issuer simulator was seeded from the recorded card brands and amounts, so the soft/hard split below is the simulator's, not ours.

Late charges are approvals landing more than an hour after the shopper left the checkout — the ones that generate a "what is this?" email.

What the numbers say

  • Delay is the whole of it. The same request an hour later recovers eight times what the same request 340 milliseconds later recovers. Nothing about the request changes; only when it is asked.
  • Two attempts is the knee. A third attempt at 72 hours adds 1.1 points of recovery for 26 per cent more attempts. It is not worth the ledger noise.
  • Sorting by decline code pays for itself. Retrying every decline rather than the soft ones costs 59 per cent more attempts and recovers three fewer. Hard declines never turn into approvals, and the fee is charged either way.
  • 428 recovered over fourteen days is 36 per cent of the declines, which against the eight-day rise takes the effective decline rate from 4.2 per cent back to about 2.7 per cent. It does not undo the rise. It is worth doing anyway, and it would have been worth doing before the rise.
Every approval on this schedule lands after the shopper has left. A charge arriving an hour later with no message is a support ticket and possibly a chargeback. The schedule is not shippable without the shopper being told — at checkout that a retry may happen, and by email when one succeeds. That is a second piece of work and it is not optional.

What this prototype is not

The sandbox's issuer simulator is not the issuers. The soft/hard split is credible because it matches the shape of the recorded traffic; the recovery rates are the simulator's model of issuer behaviour and should be read as an order of magnitude, not a forecast. The only way to know is to ship the schedule behind a flag and measure.

None of the code here is meant to be kept. What is meant to be kept is the schedule — +1 h then +24 h, soft declines only — and the finding that we cannot implement it until the decline code is persisted.
